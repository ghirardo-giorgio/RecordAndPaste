# Record and Paste

A remote control for [**Stenografa**](https://github.com/ghirardo-giorgio/stenografa) — an Android/iOS app that turns your phone into a remote microphone and a programmable button pad for the Stenografa daemon running on your PC (Linux, macOS, or Windows).

The phone becomes two things at once:

1. **A remote microphone**: tap a button, dictate, and the text transcribed on the PC is pasted into whatever application currently has focus;
2. **A button pad**: full-screen grids of buttons that run keyboard shortcuts, key sequences, text snippets, or launch applications on the PC.

Speech recognition, pasting and key execution all happen on the PC: the app records nothing locally and talks to no external service — it only sends commands to the daemon on the local network.

## The Stenografa daemon (required)

Record and Paste is a **client only**: it cannot work on its own. It requires the [Stenografa daemon](https://github.com/ghirardo-giorgio/stenografa) to be installed and running on your PC (Linux, macOS or Windows). The daemon handles transcription (Whisper), pasting, key simulation, dashboards, and everything else described below. See the daemon's repository for installation instructions, configuration and its own documentation.

## First launch

The daemon must already be running on the PC, on the same local network as the phone. On first open the app shows the connection screen, where you enter:

| Field | Value |
| --- | --- |
| PC IP address | e.g. `192.168.1.50` |
| Port | `8765` (daemon default) |
| Token | 5 digits, generated by the daemon on first start |

The token lives in `~/.config/stenografa/config.json` on the PC, and is also shown in a notification on the daemon's first start. The **Verify connection** button tests address, port and token without saving anything.

From then on the app reconnects by itself on launch and after every dropped connection, retrying every 3 seconds. The screen stays awake while the app is in the foreground (it is a button pad, not an app you glance at).

## The main screen

A full-screen grid of buttons. Horizontal swipe moves from one dashboard to another; the dots under the name show which page you are on.

Around the grid:

- **top left**: pencil (edit mode), crosshair ("follow active app"), and history when there is any;
- **top center**: the name of the current dashboard;
- **top right**: settings.

**Follow active app** (the crosshair): when on, the app switches by itself to the dashboard associated with the PC application that has focus — bring GIMP to the foreground and the GIMP dashboard appears. The association is set per dashboard (the "Detect app" field).

In landscape the grid is reflowed onto three scrollable columns, so a dashboard with many buttons stays legible instead of shrinking.

### Larger buttons

A button can occupy more than one cell. The path is: **pencil** at the top left to enter edit mode, then **long-press** the button until "Edit <name>" opens, and there the **Width** and **Height** spinners set how many cells it takes horizontally and vertically. This works for every button type, microphones included. It exists to give prominence to the ones you press most often — a "Record" twice as tall is findable without looking.

The occupied area must stay inside the grid and must not overlap other buttons: if there is no room the PC rejects the edit and says so, instead of letting them overlap. To make room, enlarge the grid first with the "rows"/"columns" bars. While dragging, two buttons swap places only if they have the same shape.

### Colors and the application icon

Buttons come in a palette of eight tints — Coral (the accent), Amber, Olive, Emerald, Cerulean, Indigo, Magenta and Slate (the neutral of buttons with no color of their own) — chosen to stay readable with the white label on top and not to clash with each other when the grid is full.

When a dashboard is associated with a PC application (because it contains a "Launch application" button, or has a "Detect app" that identifies it), **the real icon of that application** appears large at the center of the screen, behind the grid, with a halo of light that lifts it off the background. Buttons are slightly translucent, so the icon peeks through them without hurting label readability: you can tell at a glance which dashboard you are on.

"Launch application" buttons also show the app's real icon instead of a generic symbol, so they are recognizable at a glance. If you prefer a different icon you pick it from the editor: your choice always wins over the automatic one.

Icons come from the PC, not from the internet: on Linux from `.desktop` files and installed icon themes (the SVG is converted to PNG when needed), on macOS from the `.icns` inside the app bundle, on Windows from the executable or the package assets. If an application has none, it falls back to the generic symbol.

### Dictation state

"Microphone" buttons change appearance following the daemon's state: gray at rest, **red** while recording, amber while transcribing, purple while the AI is processing, blue while loading the model. The phone vibrates at the start and end of recording, because the daemon's written feedback is a notification on the PC — exactly where you are not looking.

One recording at a time: while one is in progress, the other microphone buttons go dark and show "Busy with another button". Only the one that started it can stop it, so text cannot end up in the wrong channel (a normal dictation stopped by the AI button, or vice versa).

## Button types

| Type | What it does when pressed |
| --- | --- |
| **Microphone** (`record`) | Starts/stops dictation; the transcribed text is pasted into the focused window on the PC. |
| **AI voice command** (`ai_command`) | You dictate a command instead of a text: a local LLM (LM Studio on the PC) interprets it and runs the matching shortcut — say "copy" and Ctrl+C is pressed. Shortcuts of the same dashboard take priority. |
| **Shortcut** (`keys`) | Simulates a key combination, e.g. `ctrl+shift+z`. |
| **Macro** (`macro`) | Runs several combinations in sequence, with a configurable pause between steps (max 20 steps). If a step fails the sequence stops. |
| **Text** (`text`) | Pastes a fixed snippet: signatures, recurring prompts, long paths (max 5000 characters). |
| **Launch application** (`launch`) | Launches an installed application on the PC, picked from a list. The button shows **the application's real icon** instead of a generic symbol. |
| **Paste last** (`paste_last`) | Re-pastes the last dictation without recording a new one: for when the cursor was not where it should be and the text landed in the wrong place. |

Pasting is adaptive: in terminals the daemon uses `Ctrl+Shift+V` instead of `Ctrl+V`. If automatic paste fails, the text stays on the clipboard anyway and the PC reports it.

### Auto-enter

On the record button there is an **"Enter" checkbox** at the bottom right: when on, after pasting the dictated text the PC presses **Enter**. In a chat the message sends itself — dictate and done, no keyboard needed.

You toggle the checkbox with a tap, without entering edit mode: it is a choice that changes often — needed in chat, not in an editor. It applies to that button only and only to normal dictation: the AI voice command pastes no text, and "Paste last" never presses Enter.

### Push-to-talk

By default microphone buttons work as a toggle (tap to start, tap to stop). With push-to-talk on, they record for as long as you hold them down — more comfortable for short sentences. As a safety net the daemon stops a recording on its own after 3 minutes.

## Voice activation

Start and stop dictation by speaking a phrase, without touching any button. Turned on from settings, under *Voice activation*, which has **two independent switches** — you can keep both on:

- **Listen on the PC**: the daemon keeps the microphone open. The most comfortable option: it works with the phone in your pocket or off, and uses no battery.
- **Listen on the phone**: the app listens with the phone's microphone, using the system speech recognizer. Works **with the app open**. Useful when you are far from the PC and its microphone would not hear you.

The **two phrases** — one to start, one to stop — are written once and apply to both listeners (they are daemon settings, so they follow the PC and not the individual phone). By default they are `jarvis` and `jarvis stop`.

Choose words you would not say by accident while talking: an invented name works better than a common word. At least 3 characters are required, and the two phrases must be different from each other. The recognizer tolerates transcription errors — up to a quarter of the letters — so "Jarvis Top" counts as "Jarvis stop". If the phrases end up in the dictated text, the PC strips them out before pasting.

### If the PC has no GPU

If Whisper cannot use the graphics card on the PC (absent, missing drivers, or VRAM busy with something else), transcription there takes roughly real time. In that case **the phone transcribes**, on its own and with nothing to configure: the app uses Android's speech recognition — the same one behind the keyboard's microphone button, but without a keyboard on screen — and sends the PC ready-made text, pasted as usual.

The text arrives right away instead of making you wait, but punctuation is poorer and the dictation vocabulary does not apply: Android's recognizer accepts no hints. The app must be in the foreground, because it is the phone's microphone doing the listening.

When the GPU becomes available again, transcription moves back to the PC.

### If you forget to stop it

After ten seconds without hearing you speak, the dictation closes by itself and pastes what it collected — convenient precisely with voice activation, where forgetting the stop phrase is easy. The wait is adjustable (or disableable) from *Close on silence* in settings.

It does not apply to push-to-talk, where the finger does the closing, and it never fires while the dictation is shorter than the configured wait: a recording that has just started is not closed merely because you have not spoken yet.

### When the phrase is heard differently

The speech recognizer writes what it hears **in the dictation language**: an invented word like "Jarvis", said in Italian, often becomes "already seen" or something close. On the PC the problem is solved by suggesting the spelling to the model, but the Android and iOS recognizers accept no suggestions.

For this reason every field accepts **multiple forms separated by commas** — one match is enough:

```text
Start phrase:  jarvis, already seen
Stop phrase:   jarvis stop, already seen stop
```

Under the fields you see **the last phrase heard**, split between PC and phone: that is where you read how it is really being heard, and then add that spelling. Avoid listing expressions you actually use while talking ("already seen" would be one): they would become a way to start a dictation by mistake.

While you dictate, the stop phrase is searched only at the end of what the phone heard: the microphone also hears the text you are dictating, and searching the whole speech would cut the dictation short mid-sentence.

### The activation sounds

The chirp you hear at the start and end of listening comes from Android's speech recognizer, and it plays on every **listening session**, not on every dictation. Sessions are closed and reopened by the system even when nobody speaks, so the phone keeps beeping for nothing.

Two countermeasures, in the order they became necessary:

1. The session is kept open for a long time (ten minutes, in "dictation" mode, which tolerates pauses) instead of being closed at the first silence. It reduces the number of sessions, but is not enough: Android closes them on its own anyway.
2. The beeps are **muted while waiting for the phrase** and restored during dictation, the only moment they say anything useful. There is no official way to ask the recognizer to stay quiet, so the audio streams carrying those sounds are muted (see `MainActivity.kt`): the silence also covers the phone's media audio while waiting. Disabled with *Mute the activation sounds* in settings.

Only the streams muted by the app are restored — if you had muted one yourself it stays as it was — and the restore happens even if the app is closed while listening is active.

An alternative that sounds natural — starting the recognizer only when a voice is heard — does not work in practice: the detector would fire *during* the word, and the recognizer takes a few hundred milliseconds to start, hearing only the tail of the activation phrase.

### Seeing that the PC is recording

When dictation starts by voice you touch nothing, so the PC shows a box at the bottom of the screen with a pulsing red dot. It is drawn by a GNOME extension installed with the daemon: until it is active (on Wayland it loads at the next login) nothing appears. See "Voice activation" in the daemon's [README](https://github.com/ghirardo-giorgio/stenografa).

When the start phrase is recognized, the app presses the microphone button of the open dashboard for you: the dictation therefore inherits that dashboard's vocabulary and auto-enter, as if you had tapped it. The stop phrase only stops a dictation in progress.

If at least one listener is on, an ear icon appears at the top left: it exists so you never leave a microphone open without knowing. The microphone permission is requested the first time phone listening is used; if denied the app says so, instead of leaving the switch on for nothing.

## Edit mode

Entered with the pencil at the top left. In this mode buttons no longer run their actions: they are there to be rearranged.

- **Add**: tap an empty cell and choose the button type.
- **Move**: drag the button onto another cell.
- **Delete**: the ✕ at the top right of the cell. The last microphone button in the layout cannot be deleted, so you are never left without a way to dictate.
- **Edit**: long-press a button. From there you change **name**, **action** (key combination, macro sequence with its pause, text snippet), **color** and **icon** — without rebuilding the button from scratch, keeping its position and look.
- **Resize the grid**: the "rows" and "columns" bars at the edges add or remove cells.

---

## Dashboards

Every dashboard is an independent grid, usually dedicated to one PC application. You switch between them with a swipe.

In edit mode, tapping the **dashboard name** at the top opens its options: reorder, duplicate, delete, or open its settings:

- **Name** — also to rename it;
- **Detect app** — the text to look for in the name or title of the focused window on the PC (e.g. `code` for Visual Studio Code): it is what lets "follow active app" pick this dashboard;
- **Dictation vocabulary** — terms specific to that application (e.g. `InvokeAI, denoising, checkpoint`), used to transcribe its jargon correctly when dictating from a button on this dashboard.

To **create a new one**: pencil → "+" icon in the left bar → name → Create. (Alternatively, again in edit mode, swipe to the "+" page at the end of all dashboards.)

## Settings

Reached from the gear at the top right.

**Connection** — address, port, token, with connection verification.

**Phone-local preferences** (not shared with the PC):

- *Hold to talk* — push-to-talk;
- *Vibration* — haptic feedback at start/end of recording;
- *Follow active app* — also toggled from the crosshair on the main screen;
- *Listen on the phone* — voice activation with the phone's microphone (see [Voice activation](#voice-activation)).

**Daemon settings** (shared: they apply to every connected phone):

- *Dictation language* — 20 languages plus automatic detection;
- *Restore clipboard* — puts back what was on the clipboard before the paste;
- *Automatic translation* — translates the dictated text before pasting, via Whisper (to English only) or via a local LLM (any language);
- *Pause videos while dictating* — stops playback when dictation starts and resumes it when it ends (see [Media controls](#media-controls));
- *Confirm before pasting* — the dictated text appears on the phone and is pasted only after approval (editable before sending);
- *Global vocabulary* — terms to transcribe correctly in any context;
- *Close on silence* — after how many seconds of silence the dictation stops and pastes by itself (10 by default, "Never" to disable);
- *Voice activation* — PC listening and the two phrases that start and stop dictation (see [Voice activation](#voice-activation));
- *Restart daemon* — useful after updating its code, no terminal on the PC needed.

**Security** — connection state (encrypted or clear), certificate fingerprint and the *Require TLS* switch.

## Media controls

When something is playing on the PC (a video or music), a small button appears under the gear for each stream: **pause** while it plays, **play** when it is stopped. It exists to stop what is playing before dictating, without going back to the keyboard — otherwise the microphone picks up its audio and the transcription comes out ruined — and to start it again when you are done.

Paused videos are shown too, so opening the app still gives you the button to resume them. The icons are few by construction: a browser exposes one player per window, not per tab. If several streams are present, several icons appear (up to five); the tooltip shows each title, so you know which one you are stopping.

Detection uses **MPRIS**, the D-Bus standard exposed by browsers and players on Linux (the same one KDE Connect relies on). On Windows and macOS it is not implemented and the icons do not appear. The same video published on several buses — it happens with the Plasma browser integration — is shown only once.

The *Pause videos while dictating* setting (off by default) automates all of it: the PC stops playback by itself when dictation starts and resumes it when it ends. What was paused by hand from the phone is not resumed by the automation.

### Several tabs playing at once

Chromium-based browsers (Chrome, Brave, Edge) publish **a single MPRIS player per window**, the one of the tab playing "in the foreground" in their internal bookkeeping: if two tabs play at the same time, the second is not visible and there is no way to pause it. It is a browser limitation, not the daemon's — the desktop's media widgets show one tab per browser too.

For that case, the automation makes a second pass over the **audio streams**: PipeWire sees a separate track for every playing tab, so whatever the players did not stop is muted for the duration of the dictation and unmuted at the end. The video keeps playing, but silently, so it never ends up in the transcription. Streams that were muted by hand are left alone.

## Dictation history

The clock icon, when there are dictations, opens the list of the last 20 (kept only in the daemon's memory, so it resets when it restarts). From there a past entry can be re-pasted: only its identifier travels, not the text, because the daemon only agrees to paste what it has already produced.

The "Paste last" button is the shortcut to the most recent entry.

## Security

- **5-digit token** generated by the daemon: without it the connection is closed immediately. The daemon temporarily blocks an IP after 5 failed attempts in 60 seconds.
- **TLS with a self-signed certificate** generated by the daemon. Since no authority vouches for it, the app uses *trust on first use*: it accepts the certificate seen at the first connection and from then on requires it to be identical. If it changes (daemon reinstalled, or someone impersonating the PC) the connection stops and asks for an explicit confirmation, showing the two fingerprints side by side.
- **Require TLS**: the daemon refuses clear-text connections. The app never falls back to clear text with a PC whose certificate it has pinned: a failed handshake is a network problem and is retried.
- An authentication refusal always says *why*: only a genuinely wrong token stops the attempts (fix it by hand), while temporary refusals retry on their own.

## Project structure

```text
lib/
├── main.dart                    theme and startup
├── models/
│   ├── button_spec.dart         ButtonSpec, Dashboard, icons and colors
│   ├── connection_settings.dart address, port, token
│   └── daemon_state.dart        daemon states (idle, recording, …)
├── screens/
│   ├── home_screen.dart         grid, edit mode, dialogs
│   ├── settings_screen.dart     connection and preferences
│   └── history_screen.dart      recent dictations
├── services/
│   ├── steno_client.dart        TCP/TLS client and JSON protocol
│   ├── settings_service.dart    local preferences (SharedPreferences)
│   ├── wake_word_service.dart   activation phrase listening
│   ├── wake_phrase.dart         tolerant phrase matching
│   └── locale_service.dart      interface language
└── l10n/strings.dart            strings in Italian and English
```

### The protocol in brief

JSON lines separated by `\n` over TCP (encrypted when the daemon has a certificate). The phone sends `{"cmd":"auth","token":"…"}` first; after the `{"type":"auth","ok":true}` reply it receives state, layout, configuration and history, and can send commands (`button`, `add_button`, `edit_button`, `create_dashboard`, …). Updates arrive as `state`, `layout`, `result`, `history`, `active_app` messages. The authoritative definition lives in the daemon repository (`daemon.py`).

```bash
flutter pub get

```

### Screenshots without a phone

`test/screenshots_test.dart` builds the main screen with a hand-filled client and saves PNGs into `test/goldens/`, with no device or emulator needed:

```bash
flutter test --update-goldens test/screenshots_test.dart
```

They cover the idle grid, recording in progress with the other microphones locked, the media controls, the button editor, the dashboard options and settings, and dashboard creation. The images depend on system fonts, so a difference in the automatic comparison is not necessarily a regression.
